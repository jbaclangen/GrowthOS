# Braventa (codename GrowthOS)

Braventa is a business growth system for small and mid-sized service businesses: it connects website,
marketing, CRM, and content into one system that shows what to do next and helps get it done.
Tagline: "Run your growth as one system." Public name is **Braventa** — never "Braventa AI", never "GrowthOS"
in anything a user sees (D-001/D-002). "GrowthOS" survives only in code identifiers and history.
Phase: MVP proof of concept, not yet charging customers.

## Source-of-truth hierarchy
1. Explicit, recent founder decisions (in chat, `docs/decisions/FOUNDER_BRIEF_2026-10-10.md`, or `DECISION_LOG.md` entries marked Founder).
2. Approved product and brand specifications (`docs/brand`, `docs/product`, `design-system`).
3. Approved architectural decisions (`docs/architecture`, this file's rules).
4. Current implementation and verified behaviour.
5. Product vision and planning context (`docs/product/GrowthOS_Product_Vision_and_Planning_Context.md`, D-019).
6. Unapproved proposals and roadmap ideas.
When a request conflicts with the docs, say so and confirm the intended change before rewriting a foundational
decision. Never describe the product as doing something the code doesn't do, whatever a spec says.

## Working rules
- Treat approved specs as the source of truth; keep naming, positioning, voice, tokens, and UI conventions consistent.
- Never invent capabilities or present planned features as live. Live today: website analysis + pain-point discovery → business
  profile → growth score + diagnosis the owner confirms or corrects → one prioritized growth plan (accept / dismiss /
  done) → 30-day plan → 5 drafted posts with approve/reject. No CRM, publishing,
  email sending, automation, analytics, or billing yet.
- Check `MVP_SCOPE.md` before adding features; prefer small, testable changes over rewrites.
- Style only with design tokens and shared primitives: semantic Tailwind roles (`bg-surface`, `text-muted`,
  `bg-accent`, …), `.btn-primary/.btn-secondary/.input/.card/.chip/.eyebrow`, `<Logo />`. No HEX in components,
  no `dark:` colour overrides. Change values only in `design-system/tokens.json`, then `npm run tokens`.
- Typography (founder decision D-015): Quicksand for headings, Comfortaa for everything else. Logo (D-027): outlined Montserrat ExtraBold B on a tile with a Violet dot + BRAVENTA.IO in outlined Quicksand Medium — use `<Logo />` or the generated files, never typeset it.
- Brand assets are generated by `design-system/scripts/build-brand-assets.mjs` — never hand-edit files in `web/public/brand/`.
- Copy: US English, sentence case, verbs on buttons, errors say what happened and what to do, no hype or guarantees.
- Preserve tenant isolation, security, accessibility (WCAG 2.2 AA), and privacy.
- Don't change brand strategy, positioning, or core messaging (D-005) without the founder's authorisation.
- When behaviour, integrations, architecture, or branding change: update the relevant doc, and record significant
  decisions in `DECISION_LOG.md` (new entry; mark old ones Superseded). Add unresolved items to `OPEN_QUESTIONS.md`.
- Surface conflicts between code, requests, and docs instead of silently picking one.
- Verify (typecheck, lint, `npm run tokens:check`, and the running app for UI changes) before reporting completion.

## Architecture rules (do not break)
- Supabase is the system of record. n8n only executes workflows and calls back to `/api/n8n/*` (planned — those
  routes don't exist yet; the MVP pipeline runs in-process via `after()`).
- Every tenant table has `organization_id` + RLS via `public.is_member()`. New tables must too.
- AI calls go through `web/src/lib/ai/router.ts` (`runWorker` / `runWorkerJson`) — never call OpenRouter directly
  from features. It enforces the monthly budget and logs `ai_usage`.
- Secrets are server-only (`web/src/lib/env.ts`, `import "server-only"`). Never `NEXT_PUBLIC_` a secret.
- `createSupabaseAdminClient()` bypasses RLS: only for trusted server code, and always scope by an
  organization id you have already authorised.
- Human approval is the default before anything is published for a client (D-013).
- Crawled website content and customer documents are untrusted input to models.

## Commands (run in `web/`)
- `npm run dev` — dev server; `GET /api/health/integrations` checks every external service.
- `npm run build`, `npm run lint`
- `npm run tokens` — compile `design-system/tokens.json` → `src/styles/tokens.css` (fails on WCAG contrast); `npm run tokens:check` verifies it's current.

## MVP demo flow
login → `/onboarding` (website URL + optional goal, service area, tools — BI-12) → `startAnalysis` creates an
`onboarding_sessions` row and queues a `website_evidence` job (crawl + PageSpeed → business profile) via `after()` →
`/onboarding/[sessionId]` discovery (pain points + free text, D-028) → `/review` (confirm, top three) → `/questions` (up to 4
adaptive follow-ups, ON-5) → `startPlanIfReady`
queues one `website_plan` job once discovery is done and evidence succeeded → `/analysis/[id]` polls until done.
Plan: growth score + diagnosis + growth plan (`diagnoses`, `diagnosis_findings`, `growth_plan_items`) → 30-day plan → 5
drafted posts (status `needs_approval`). Owner corrections queue a `diagnosis_update` job (diagnosis step only).
Re-run queues `website_intel`, which does both halves with the latest finished discovery. `AI_MODE=free` uses OpenRouter free models (~3–4 min per run, ~50 free requests/day).
Pages read cookies, so with Cache Components their content must sit inside `<Suspense>`.
